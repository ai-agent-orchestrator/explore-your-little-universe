# DB 추가 개발 제안 — 사법·의료·시장 DB의 필수 실무 기능 5가지

2026-11-22 · 추가 설계 제안 · 이 문서는 구현된 기능이 아니라 **다음 단계 제안**이다.

타로 × PostgreSQL × Neo4j × Chroma × LangGraph 서버 모드([설계서](TAROT_3DB_LANGGRAPH_PLAN.md), [구현 인계서](CLAUDE_TAROT_IMPLEMENTATION.md))에 이어, 사법·의료·시장(금융·상거래) 분야의 DB에서 거의 항상 요구되는 기능 5가지를 이 프로젝트에 연습용으로 얹는 방안이다. 타로 데이터에는 민감정보가 없으므로 같은 패턴을 안전하게 시험하기에 알맞다.

> **주의**: 아래는 설계 패턴 제안이다. 실제 사법·의료·금융 서비스에 쓰려면 해당 분야의 법령·규제 검토와 별도 보안 점검이 필요하다. 이 문서는 컴플라이언스 인증이나 법률·의료 자문이 아니다.

## 전제와 확인 상태

- 설계서 §4의 `reading_sessions`, `reading_draws`, `reading_reports`, `reading_events`와 LangGraph 체크포인터(`thread_id = session_id`)를 이미 있는 것으로 본다.
- LangGraph 1.2.24 설치본에서 `Send`, `interrupt`, `Command`, `PostgresStore`, `PostgresSaver`, `update_state`, `get_state_history`가 **존재하는 것까지만 확인**했다. 각 기능의 동작은 아래 제안 항목을 구현할 때 테스트로 확인한다.
- 문서의 목표를 이미 구현된 기능이나 측정된 성과로 쓰지 않는다.

## 추천 순서

아래 본문의 번호가 곧 권장 구현 순서다(1 → 2 → 3 → 4 → 5).

| 순서 | 항목 | 이유 |
| --- | --- | --- |
| 1 | 감사 추적과 재현성 | 현재 코드에 바로 얹을 수 있고, 나머지 기능의 전제가 된다 |
| 2 | 개인정보 보호·접근 제어·보존·삭제 | 질문 원문이 세션 테이블과 체크포인트 두 곳에 남으므로 조기에 필요 |
| 3 | 문장 단위 근거 검증 | LangGraph 구조가 `Send` 병렬로 바뀌는 큰 작업 |
| 4 | 사람 승인 흐름 | 3번의 비평 결과가 있어야 검토 대기열이 의미를 가진다 |
| 5 | 시점 기반 지식 | 지식 데이터가 충분히 늘어난 뒤에 해도 늦지 않다 |

## 1. 감사 추적과 재현성

**왜 필수인가** — 사법은 증거 보관 이력, 의료는 접근·변경 기록, 금융은 의사결정 기록이 필요하다. "그때 왜 그 답이 나왔는지"를 나중에 같은 조건으로 재현할 수 있어야 한다.

**DB 쪽 개발**

- `reading_attempts` 테이블: 재작성 시도마다 초안, 검증 오류, 모델 ID, 프롬프트 판본, 지연시간, 토큰 수를 남긴다. 현재 설계는 최종 리포트만 저장한다.
- `reading_events`에 직전 행의 해시를 포함하는 **해시 체인**을 넣어 중간 행 삭제·수정을 탐지한다.
- 인용한 청크는 ID뿐 아니라 당시 `content_hash`와 `dataset_version`을 함께 기록한다. 원문이 나중에 바뀌어도 어떤 문장을 근거로 했는지 복원할 수 있다.
- `reading_events`·`reading_attempts`는 애플리케이션 계정에 `INSERT`/`SELECT`만 허용하고 `UPDATE`/`DELETE`는 막는다(추가 전용).

**LangGraph 핵심** — 체크포인트 기록(`get_state_history`)으로 특정 시점에서 다시 실행(replay)하거나 상태를 고쳐 분기(fork)한다. 같은 카드·같은 근거로 프롬프트만 바꿔 A/B 비교하는 평가 도구의 기반이 된다.

**완료 기준**

- 임의의 세션 하나에서 최종 리포트까지의 모든 시도와 근거 판본을 조회할 수 있다.
- 이벤트 행을 직접 수정하면 해시 체인 검증이 실패한다.
- 완료된 세션을 같은 체크포인트에서 replay하면 카드·근거가 바뀌지 않는다(새 뽑기 없음).

## 2. 개인정보 보호, 접근 제어, 보존·삭제

**왜 필수인가** — 의료 정보, 소송 기록, 금융 거래는 모두 개인정보 보호와 보존 기간 규정의 대상이다. 현재 설계는 질문 원문이 `reading_sessions`와 LangGraph 체크포인트에 모두 남는다.

**DB 쪽 개발**

- PostgreSQL **행 수준 보안(RLS)**: 세션 소유자만 자기 행을 읽도록 한다. 현재는 토큰 해시를 애플리케이션 계층에서만 확인한다.
- 질문 필드 암호화(애플리케이션 수준 또는 `pgcrypto`). 키는 환경 설정으로 분리하고 저장소에 넣지 않는다.
- **삭제 작업**: `session_id`(= `thread_id`) 기준으로 세션, draw, 리포트, 이벤트, **체크포인트까지 한 번에** 삭제한다. 삭제 후 각 테이블에서 해당 ID가 남지 않았음을 검증한다.
- 보존 기간(TTL) 정책과 정리 작업. 기간은 설정으로 둔다.
- 감사 로그(1번)와 충돌하지 않도록 **감사 로그에는 질문 원문을 넣지 않고** 해시·ID만 남긴다.

**LangGraph 핵심** — 그래프 맨 앞에 **마스킹 노드**를 두어 이름·연락처 같은 패턴을 LLM 호출과 로그에 들어가기 전에 가린다. 마스킹 전 원문이 체크포인트에 남지 않도록 상태 설계를 먼저 정한다.

**완료 기준**

- 다른 소유자의 `session_id`로 조회하면 DB 수준에서 0행이다(애플리케이션 필터 없이 RLS만으로).
- 삭제 요청 후 체크포인트 테이블에도 해당 `thread_id` 행이 없다.
- 마스킹 노드 테스트: 전화번호·이메일 형태가 LLM 입력 페이로드에 나타나지 않는다.

## 3. 문장 단위 근거 검증

**왜 필수인가** — 존재하지 않는 판례를 인용한 사고가 대표적이다. 의료에서는 출처 없는 권고가, 금융에서는 근거 없는 수치가 위험하다. 현재 검증기는 **인용 ID가 이번 검색 결과에 존재하는지**만 확인하며, 본문이 근거와 모순되는지는 잡지 못한다.

**DB 쪽 개발**

- `report_claims` 테이블: 리포트 문장 단위로 `claim_text`, `chunk_id`, `support`(`supported`/`partial`/`unsupported`)를 저장한다.
- 근거 커버리지 지표: 카드별 지지된 문장 비율. 평가 세트(30문항)에서 지표를 비교한다.

**LangGraph 핵심**

- **비평(critic) 노드** 추가: 비평은 실패 사유를 **추가할 수만** 있고 코드 검사를 대신 통과시킬 수 없다(설계서 원칙 유지).
- `Send` 병렬화: 카드 3장을 각각 별도 작성·검증하고 합친다. 실패한 카드만 다시 쓰면 호출 비용이 줄고 실패 원인을 카드 단위로 추적할 수 있다. 재작성 상한(2회)은 카드별로 적용한다.

**완료 기준**

- 일부러 근거와 반대되는 문장을 넣은 FakeLLM 초안이 `unsupported`로 걸러진다.
- 한 카드만 실패했을 때 나머지 두 카드의 생성 호출이 반복되지 않는다.

## 4. 사람 승인 흐름 (maker-checker)

**왜 필수인가** — 변호사 검토, 의사 서명, 금융 컴플라이언스 승인은 모두 "AI가 초안, 사람이 확정" 구조다. LLM이 단독으로 최종 결과를 확정하지 않는다.

**DB 쪽 개발**

- `review_queue` 테이블: `session_id`, 사유(`needs_evidence`, 낮은 근거 커버리지 등), 담당자, 상태(`pending`/`approved`/`rejected`/`edited`), 코멘트, 처리 시각.
- 승인·반려 이력은 1번의 추가 전용 이벤트로 남긴다.
- 현재 설계의 `needs_evidence` 종료 상태가 대기열 진입점이 된다.

**LangGraph 핵심** — `interrupt()`로 그래프를 멈추고 검토자 입력을 `Command(resume=...)`로 이어간다. 체크포인터가 PostgreSQL이므로 서버가 재시작돼도 대기 상태가 유지된다. 검토자가 초안을 고친 경우 `update_state`로 반영하고 이력을 남긴다.

**완료 기준**

- 대기 중 프로세스를 재시작한 뒤에도 같은 `thread_id`로 재개된다.
- 승인 전에는 최종 리포트가 사용자에게 `report.completed`로 전달되지 않는다.
- 같은 세션을 두 검토자가 동시에 처리하려 하면 한 쪽만 성공한다.

## 5. 시점 기반 지식 (이중 시간, as-of 조회)

**왜 필수인가** — 법령은 개정되고, 진료 지침은 갱신되고, 시세는 바뀐다. "그 시점에 유효했던 근거"로 답해야 소급 오류가 없다.

**DB 쪽 개발**

- Neo4j 관계와 규칙 노드, Chroma 청크 메타데이터에 `valid_from`, `valid_to`(열린 구간은 빈 값 규칙을 정해 문서화)를 추가한다.
- 모든 고정 Cypher와 Chroma `where` 필터에 `as_of` 조건을 건다.
- PostgreSQL `reading_sessions`에 `as_of`를 저장한다. 기존 `dataset_version`·`mapping_version`을 시간 축으로 확장하는 작업이다.

**LangGraph 핵심** — `as_of`를 상태에 넣어 모든 검색 노드가 같은 시점으로 조회하게 한다. 옛 세션을 재개·replay할 때도 당시의 지식 상태가 유지된다.

**완료 기준**

- 유효 기간이 지난 규칙은 `as_of`가 현재일 때 반환되지 않고, 과거 `as_of`일 때는 반환된다.
- 지식 데이터를 갱신한 뒤에도 이전 세션의 replay 결과가 바뀌지 않는다.

---

## 그래프 DB 쪽 추가 후보 (이 5개에는 포함하지 않음)

Neo4j의 대표적인 실무 용도로 판례 인용 네트워크(사법), 약물 상호작용·질병 코드 체계(의료), 지분·거래 관계를 이용한 의심 고리 탐색(시장)이 있다. 타로 데이터로는 의미 있게 연습하기 어려워 5개 목록에서 제외했다. 별도의 실제 공개 데이터셋을 정한 뒤 다루는 것이 맞다.

## 구현 시 지킬 원칙

- 기존 정적 모드(GitHub Pages)와 `v1` 브랜치는 건드리지 않는다.
- 이 문서의 항목은 각각 작은 PR로 나누고, PR마다 실제 PostgreSQL·Neo4j·Chroma로 검증한 것과 fake로만 검증한 것을 구분해 보고한다.
- 건너뛴 검증을 통과로 보고하지 않는다.
- 사법·의료·금융 데이터를 실제로 넣는 단계는 이 저장소의 범위가 아니다.
